## 0. 一句话结论

SHSynth 的**数值内核已经具备多时次能力**(`SHCoeffs.C/S` 支持
`(L+1, L+1, ntime)`,`synthesize` / `evaluate` / `synthesis_grid` 的时间轴
广播一次矩阵乘就覆盖全部历元),真正缺的是**时间维的"身份、批量、产品、界面"四件事**;
外加一件**物理量**的事:**水平形变 u_N / u_E**(载荷勒夫数 `l′` 就在随包表里,
却从来没被用过):

| 缺的东西 | 一句话 |
| --- | --- |
| **身份** | 系数不知道自己对应哪一天;`meta` 里只有一个 `ntime` 计数,没有任何日期 |
| **批量** | 一次只能算一个时次:`select_time()` 把多时次压成第 0 个,再循环 203 次"运行" |
| **产品** | 写出的场序列**没有时间坐标**(写出即丢日期);没有点序列、趋势场、逐历元诊断 |
| **界面** | 界面只有一个 0..ntime−1 的"时次"数字框,没有时间轴、范围、批量进度与播放 |
| **水平形变** | 只有径向 `u_r`;北/东分量需要 `∂P̄/∂θ` 与 `P̄/sinθ` 两个新算子(极点必须用极限) |

因此本方案**只新增一个数值算子**(水平形变的球面梯度),其余全是"把时间提升为一等
公民":批量综合走"一次调用把 `ntime` 全部算完"这条 SHSynth 内核**本来就走得通**的路
——实测比逐历元循环快 **11.3 倍**,且结果逐位相同(§6)。

> ⚡ **效率另有一条独立的、更大的杠杆**:现有内核只走"显式经度展开"的直接法,
> 代价 `O(nSHCS·nlat·nlon·ntime)`;换成 **FFT 经度路径**后降到
> `O(nSHCS·nlat·ntime) + O(nlat·ntime·nlon·log nlon)`。实测纯 Python 就能拿到
> **27~125×**(1°×203 历元:8~10 s → **0.3 s**),逼近 C#/多线程/SIMD 实现的
> 0.14 s(见 §6.5,参考 `m2csharp`)。**全案的工作量重心在 IO、产品化与界面,不在数学。**

**B. 时间信息在哪儿(原样实测,未清洗)**

**C. 文件名有三套约定,不能只认一套**

```

                           └─ 开始/结束 = 年 + 积日(YYYYDOY),203 个历元实测
```

**D. 时间**不是**等间隔的(实测)**

```

```

**结论:任何"按 `ntime` 索引当时间"或"按等间隔卷积"的实现都是错的。**

**E. 水平形变:数据和因子都在手边,只差一个算子(实测)**

```

    n   l′_n          k′_n            F_n(水平) = R·l′_n/(1+k′_n)
    1   0.103582      0.026168         6.4382e+05 m
    2   0.023287     -0.305161         2.1376e+05 m
    6   0.038587     -0.090185         2.7051e+05 m

    u_N = 0.67 mm    u_E = -1.37 mm    u_r = -71.99 mm
```

就能算水平形变,不需要任何新的外部数据。**

### 1.3 实测:必须先修的三个硬缺陷

**缺陷 A —— 三维网格写出去就没有日期了(自己写的文件自己读不回来)**

```python
fieldio.write_grid("x.nc", lat, lon, grid3d)      # grid3d 形状 (91,180,4)
# 实测:xr 维度 dims = {'lat':91, 'lon':180, 'time':4}
#       coords        = ['lat', 'lon']            ← 没有 time 坐标!
#       'time' in ds.coords = False
# 再 read_grid 回来:返回 4 个值,meta 里只有 time_name='time' 与 ntime=4
#                     → **日期彻底丢失,且 CF 不合规**
```

用户的产品文件恰恰是带真日期的:

```
3_grids/CSR_GRACE_EWH_G300.nc
    ewh   dims=(time,lat,lon)  shape=(257,181,360)  dtype=float32  units='mm'
    time  dims=(time,)         shape=(257,)         dtype=datetime64[ns]
          2002-04-18T00:00:00 .. 2026-05-16T12:00:00
    全局属性:center=CSR  lmax=60  gauss_filter_km=300  grid_resolution_deg=1.0
             long_name='Equivalent water height anomaly relative to temporal mean of the record'
```

**SHSynth 读得进这个文件,却读不出它的日期 —— 一进一出就降级成"一叠没有时间的图"。**

**缺陷 B —— legacy 序列格式读不进来**

```
3_processed/GRACE SH read/CSR_rawSH60_total_216.dat
    3783 行 × 216 列(首行是历元编号表头),跳表头后 = (3782, 216)
    2*NC(nmax=60) = 3782                          ← 正好是 to_triangle().T
    SHSynth 实测:ValueError: 无法判断系数布局(3783 行 × 216 列)
                请用 --layout 明确指定 triangle / gmfcsv / matrix
```

**结论:SHKit 的三角布局与 legacy 逐值同构,只差"首行表头 + 时间列",但今天
SHSynth 连自动识别都做不到,更谈不上配对 `*_TimeInfo.dat`。**

**缺陷 C —— 十进制年的口径必须钉死,否则对表永远差 1 天**

用 `CSR_rawSH60_total_216_TimeInfo.dat`(216×4)当权威,对 203 个真实文件的
`decimal_year` 做三种口径实测:

| 口径 | 最大绝对误差 | ≤1e-6 比例 | 判定 |
| --- | --- | --- | --- |
| 头 `time_coverage_*` + **该年实际天数**做分母(闰年 366) | **4.863e-07** | **100.0%** | ✅ 正确 |
| 头 `time_coverage_*` + 分母恒 365(流传的写法) | 2.481e-03 | 71.9% | ❌ 闰年差到 1 天 |
| 文件名起止 + 闰年分母 | 1.370e-03 | 0.0% | ❌ 文件名只能兜底 |

已核实的三条构造规则:

```
y_start = f(time_coverage_start)        f(d) = year + (DOY-1)/D_year,
y_end   = f(time_coverage_end)                D_year = 366(闰年) 或 365
y_mid   = (y_start + y_end) / 2         ← 两个十进制年的**算术平均**
```

⚠️ 另有三个易踩的坑:

1. `y_mid` **不是**"日历中点的十进制年":文件头里声明的 `(mid: 20021016)` 与
   算术平均最多差 **1 天**(= 1/365 = 2.7e-3 年),按索引硬对会得到
   "最大误差 1.37e-3、0% 通过"的假失败。
2. `time_coverage_start` 有的文件写成 `2020-03-01T00.00.00.00`(**点号不是冒号**),
   `datetime.fromisoformat` 会直接抛 `ValueError`;必须只取前 10 个字符的日期部分。
3. 两侧历元集合本来就不一样(203 个 gfc vs 216 行 TimeInfo),**必须按日期配对**,
   不能按下标对齐。

> 📌 这一条也修正了姊妹文档 `SHKit/docs/多时间数据处理方案.md` §4.1 的说法
> (那里写的是"十进制年 = year + (DOY−1)/365");该文档的验收锚点"≤1e-6"只有在
> 闰年分母下才成立。SHKit 实施时应一并更正。

### 2.1 参考实现 `m2py`(`D:\华为家庭存储\mywork\1_GlobalSpatiotemporal\codes\m2py`)

用户点名要参考 m2py 的**结果显示**。逐项核对后的结论是:**数值上 m2py 没有可抄的
水平形变**(它连径向形变都没做),但它把**"系数 → 网格 → 看"这条链路的界面与

## 3. 设计原则(先定约定,再写代码)

1. **时间只以"尾轴 + 一个描述对象"存在。**
   不另起一套 `Series` 数值类。`engine`/`filters`/`units` 已经写对了 3D 广播,
   **白拿**就是最大的胜利。新代码只做"贴标签、批量、产品化"。

2. **批量 = 一次调用,不是 N 次调用。**
   `synthesis_grid(..., coeffs_with_ntime=N)` 一次算完所有历元,实测 **11.3×**、
   结果逐位相同。**任何在批量路径里写 `for k: select_time(k); ...` 的实现都算不合格**。

3. **时间元数据随系数与场一起走。**
   `SHCoeffs.times: Optional[TimeAxis]`(默认 `None` ⇒ v1.0 行为逐位不变),
   `meta["times"]` 留只读别名。双操作数运算**先校验时间轴一致**:
   `times(A) != times(B)` 要**报错**并给中文说明,绝不静默广播。

4. **对外两条主路径,并明确推荐哪一条**
   - **路径 ①(推荐)**:`GSM*.gfc` 目录 → 系数序列 →(空间滤波/换算)→ 场序列。
     读 203 个文件 0.51 s,**不经过球谐分析**,零信息损失。
   - **路径 ②(次选)**:`(time,lat,lon)` 场序列 → 逐历元球谐**分析** → 系数序列。
     那是 SHKit 的活;SHSynth 只负责把路径 ②的**输入**准备/读取好。
   > 用户手册要写进这一句:**有 gfc 就别重做球谐分析;那是 SHKit 的事。**

5. **"空间滤波"与"时间滤波"在命名与文档上物理隔离。**
   SHSynth 的 `gaussian_km` 是**球面空间**核(逐阶 `W_n`,与时间无关);
   本文出现的"滑动平均/时间滤波"是**时间**核,属 SHKit 的 `timeseries` 地盘。
   **v2.0 不在 SHSynth 里做时间滤波**(见 §8),报告里必须分别写明。

6. **不做等间隔假设。**
   实测间隔 11–370 天,`3_grids` 里有 19 处 >40 天的缺口(最大 98 天)。
   凡涉及"月/年"一律用真实 `datetime64` 差值;`ntime` 索引**禁止**当时间用。
   十进制年只作**标签与输出格式**。

7. **不重复施加、不静默降级。**
   - 源文件若已声明是"相对时间平均的异常"(`long_name` 含
     `anomaly relative to temporal mean`,用户的 `3_grids` 就是这样),
     批量路径**默认不再去均值**,并明确提示;显式 `--remove-mean` 才做。
   - 与 `3_grids` 对账时单位必须先对齐:`3_grids` 是 **mm**,SHSynth 的 ewh 是 **m**,
     差 1000 倍。软件要读 `units` 属性并**显式报告**它做了(或没做)什么换算。

8. **诚实诊断优先于自动决策。** 缺测、重复、可疑历元一律**报告**,
   不自动剔除、不自动插补。`unused_days` 必须进逐历元诊断表。

9. **只读用户数据。** `2_unzipped/`、`3_processed/`、`3_grids/` 全程只读;
   所有产物写到 `SHSynth/out/` 或用户显式指定的路径。测试不得依赖用户数据目录
   (`skipif(not exists)` 并打印跳过原因)。

10. **与 SHKit 的边界写在文件契约上,不写在 import 上。**
    SHSynth 打包时**不含 SHKit**,因此序列读取/时间轴必须在 SHSynth 内自包含实现;
    两边靠**同一套 `series_nc` 落盘契约**(§12)互操作。装了 SHKit 的环境
    额外跑一组逐位对表测试(可选,缺 SHKit 则跳过)。

11. **矢量场 = "两个共享网格与时间轴的分量场" + 派生量,不引入 4 维数组。**
    水平形变是唯一的多分量物理量。**不**把 `values` 改成 `(nlat,nlon,ntime,2)`
    (那会让 IO、绘图、GUI、对账全部要改),而是:
    `SynthResult.components = {"north": …, "east": …}`,`values` 仍留一个**标量**
    (`magnitude`,即 `hypot(N,E)`,它是旋转不变量、处处有定义,最适合当"一个场");
    方位角 `azimuth = atan2(E, N)` 单独给。这样标量场的全部既有能力(序列、
    趋势、动画、对账)对 `magnitude` 直接可用,零改动。

12. **水平形变的两个极点必须用解析极限,不许 0/0、也不许写 0。**
    实测:`P̄_nm/sinθ` 在极点对 `m=1` **有限且非零**(`Q_11 = √3`),
    对 `m≥2` 恰为 0;`∂P̄/∂θ` 由"把列递推两边对 θ 求导"得到,**全程不出现
    `1/sinθ`**,因此极点天然安全(§4.9)。`--global-grid` 含 ±90°,
    这条不是理论洁癖,是每天都会踩的边界。

13. **水平形变与径向形变的量纲一致、因子同源。**
    两者都由载荷位驱动、`(2n+1)` 恰好约掉:
    径向 `R·h′_n/(1+k′_n)`、水平 `R·l′_n/(1+k′_n)`。
    **不要**给水平乘 `(2n+1)/3` 或 `ρ̄/ρ_w` 之类的项(那是 EWH/面密度的因子);
    实测两者同为 mm 量级,乘错立刻差 1e7 倍(§1.2 E)。

**日期来源的权威顺序(实测钉死)**

```
gfc 头 time_coverage_start/end  >  time_period_of_data 的 (mid: YYYYMMDD)
                                >  文件名  >  用户显式给定
```

- **`values`(代表日期)= 时段日历中点** `start + (end-start)/2`;
  `start`/`end` 同时保留在对象里(画图/诊断要用)。
- **`decimal_years` 的默认口径 = legacy 完全口径**(§1.3 缺陷 C):
  `y_start = year+(DOY-1)/D_year`,`y_mid = (y_start+y_end)/2`;
  没有 `start/end` 时退化为 `f(values)`。提供 `denominator='actual'|365` 以便对表。
- 头里的 `(mid: YYYYMMDD)` **不用于** `decimal_years`,只作为一致性交叉检查:
  与算术平均差 >1.5 天就报冲突(实测该差最大恰为 1 天)。
- 日期字符串清洗:`lstrip(": ").strip()`,并且**只取前 10 个字符**做日期
  (兼容 `2020-03-01T00.00.00.00` 这种点号写法)。

### 4.2 `SHCoeffs` 的改动(`coeffs.py`)

```python
@dataclass
class SHCoeffs:
    C: np.ndarray
    S: np.ndarray
    meta: dict = field(default_factory=dict)
    times: Optional[TimeAxis] = None          # ← 新增,默认 None,向后兼容

    # 新增 / 收紧
    @property
    def has_time(self) -> bool
    def time_slice(self, idx) -> "SHCoeffs"           # 单历元,返回 2D(times=None)
    def select_times(self, t0=None, t1=None, idx=None) -> "SHCoeffs"
    def with_times(self, times) -> "SHCoeffs"
    def _require_same_times(self, other) -> None      # __add__/__sub__ 调用
    def degree_rms(self, *, time=None) -> np.ndarray   # time=None → 逐历元 (ntime, L+1)
    def power(self, *, time=None) -> np.ndarray        # 同上;旧调用行为不变
```

**顺手修掉的两个既有隐患(都加回归测试)**

- `degree_rms()` 现在对 3D 把 C/S/**时间三者一起平均**:实测 `C[1,0,:]=[1,2,3,4]`
  (其余元素为 0)给出 `1.3693 = sqrt((1+4+9+16)/16)` —— 分母 16 是 n=1 这一阶的
  **全部 C/S 元素 × 时间**,被 12 个零摊薄;而 `power()` 是逐时次**求和**
  (给出 `30 = 1+4+9+16`)。两者时间语义不一致且名字看不出来。新增 `time=` 参数
  使默认行为显式,并让谱图在序列上画 **min–max 包络 + 均值**而不是一条假曲线。
- `truncate()` / `apply_degree_filter()` / `units.convert()` 都要**透传 `times`**;
  现在 `truncate` 只保留 meta,会把 `times` 丢掉。
- `__add__` / `__sub__` 现在返回 `{"op": "add"}` —— **`field_unit` 直接消失**,
  后续换算会拒绝或错换。改为保留并合并 meta,并调用 `_require_same_times`。

   finite_frac, area_mean_vs_C00, unused_days, n_warnings, warnings`。
- `outliers()` 用 MAD 稳健离群,**只报告不剔除**;人工注入坏历元要能被检出。
- **趋势/周年在系数域算**:时间算子是线性的、与空间基可交换,所以
  "先算系数序列 → 拟合 → 再综合成场"与"逐点拟合场"**机器精度一致**,
  而代价从 `O(npoints·ntime)` 降到 `O(ncoef·ntime)`(L=60 时 ncoef=3721,
  比 1° 全球 65 160 点小 17 倍)。
- **不自动去均值**:源声明异常与否决定默认行为,并写进报告(设计原则 7)。
- **矢量产品**:`synth_series` 在 `component='horizontal'` 时,每个历元产出
  `{"north","east"}` 两组场 + 派生的 `magnitude`/`azimuth`;
  `values` 取 `magnitude`,`SeriesResult.components` 带两份原始分量(设计原则 11)。
  `series_at_points(..., component=...)` 对水平返回 4 列
  `lon, lat, north, east`(可再给 `magnitude`/`azimuth`),站点序列图默认画分量。

### 4.4.1 实测:区域平均两种口径到底差多少(⚠️ 结论与直觉相反)

实现 `basin_average` 时先做了一件必须先做的事:**验证"两种方法"是不是真的
是两个答案**。结果不是 —— 当 `coeff` 建核用的掩膜格点与 `spatial` 综合用的
格点是**同一套**、`nmax` 也相同时,两者**代数上恒等**:

```
Σ_{n≤L,m} f_nm·g_nm  =  Σ_i w_i·f^L(x_i)
```

左边把 `Σ_nm f_nm·Y_nm(x_i)` 换成逐点综合值 `f^L(x_i)` 就得到右边 —— 也就是
说 `coeff` **不是另一个数值答案,而是一次等价改写**;它的价值是**算得快**。

探针 `docs/probes/_probe_basin.py`(exit=0)实测:

| 检查 | 结果 |
|---|---|
| 常值场 `C₀₀=7.5`(归一化硬锚点) | `spatial` 偏差 **1.8e-15 / 2.7e-15**,`coeff` **0.0**(精确) |
| 同一套格点两口径相对差(全球/锐利箱/平滑掩膜 × 45×90 / 90×180 / 180×360) | **6.4e-16 … 5.2e-15** ← 恒等成立 |
| 真实 203 历元序列上的两口径差 | max **7.11e-15**,RMS 1.38e-15(相对 5.4e-13%) |
| 全球掩膜 → `C₀₀` 的离散化误差(45×90 → 360×720) | 3.03e-7 → 7.39e-8 → 1.84e-8 → 4.59e-9,倍率 **0.242/0.248/0.250** ← 干净的 O(Δ²) |
| **耗时**(203 历元,nmax=60,6 516 格点掩膜) | `spatial` **1.059 s** vs `coeff` **0.022 s** → **48.5×** |

所以照原方案"报出两种方法的差异表"会报出一张**恒为舍入噪声的表**,并诱导读者
以为两个口径在互相校验。**改为**:默认两者都算并断言恒等(互为交叉验证),
再用 `mask_kernel` 打开唯一真正会分岔的场景 ——

> 现实中流域边界是**高分数字化**的,而场只在**粗网格**上综合。

`mask_kernel=(lat, lon, mask)` 只用来建球谐核,`spatial` 仍按粗掩膜算。实测
(参考 = 360×720 细网格上的 `spatial`,箱掩膜 −20..20°N / 80..40°W):

| 粗网格 | `spatial` 相对参考 | `coeff`(细核)相对参考 | 两口径差 |
|---|---|---|---|
| 45×90 | 1.21e-05 | **4.44e-15** | 1.21e-05 |
| 90×180 | 1.64e-07 | **4.44e-15** | 1.64e-07 |
| 180×360 | 3.75e-08 | **4.44e-15** | 3.75e-08 |

`coeff` 用细核时**完全不随粗掩膜网格变化**(三档都是 4.44e-15,即参考自身的
收敛极限),而 `spatial` 的掩膜边界误差随网格变粗按 Δ² 增大。这才是该看的对比。

**给用户的话**(`basin_compare` 摘要与 `series-basin` 输出都照这个口径写):
没给 `--mask-kernel` 时两个口径在同一网格上恒等,差异**应当只是浮点舍入**;
若显著大于舍入,那是实现有 bug,不是"两种方法本就不同"。

### 4.4.2 去均值的三种口径(以及 legacy 脚本里的一个坑)

去均值决定了**整个异常场的静态基准**,不是个可以顺手勾一下的小开关,所以
v2.0 把它做成三选一(默认**:不做**):

| 口径 | 含义 | 窗口 |
| --- | --- | --- |
| `grace` | **GRACE 惯例** | 2004-01-01 .. 2010-12-31 的平均 |
| `all` | 全时段 | 所有历元的平均(等同旧的 `--remove-mean`) |
| `custom` | 自定义 | 用户给的起止日期 |

**GRACE 惯例的依据**是用户自己的 legacy 脚本
`3_processed/read_GRACE_SH_preprocess_postprocess_SH60.m` 第 38-45 行
(GRACE-FO 版在同位置):

```matlab
%% remove the mean of 2004-2010
dur_mascon = 90:150;
replace_deMean_SHC = replace_SHC - mean(replace_SHC(:,dur_mascon),2,'omitnan');
```

⚠️ **但两个文件里的 `dur_mascon` 不一样**:GRACE 版写 `90:150`,GRACE-FO 版写
`19:90`。说明那是**各文件里的位置**,不是口径本身。探针
`docs/probes/_probe_demean.py` 在真实 CSR RL06(203 历元)上实测:

| legacy 写法 | 实际落到的日期 | 与注释 "2004-2010" |
| --- | --- | --- |
| `19:90` | 2004-01-07 .. 2009-12-16(72 个) | 大致相符(是 2004–**2009**) |
| `90:150` | 2009-12-16 .. 2016-01-16(61 个) | **差了 6 年** |
| 按日期 2004-01-01..2010-12-31 | 2004-01-07 .. 2010-12-14(84 个) | 就是注释的字面口径 |

**结论**:`90:150` 与它自己的注释对不上 —— 拿那个索引去跑 RL06 数据,会**静默地**
用 2009-2016 当基准,而不是 2004-2010。所以 v2.0 **按日期**实现,并把实际用到的
历元数与区间报出来:

```
预处理 : 去均值口径 = GRACE 惯例:减 2004-01-01 .. 2010-12-31 的平均;
         实用 84/203 个历元(2004-01-07 .. 2010-12-14,占 41.4%)
```

要精确复刻 `19:90`(即 2004–2009),用自定义:
`--remove-mean-mode custom --mean-from 2004-01-01 --mean-to 2009-12-31`。

**这个选择有多大影响**(探针实测,300 km 高斯 + EWH,2° 网格):

| 口径 | 用到的历元 | EWH 全局 RMS |
| --- | --- | --- |
| GRACE 惯例(2004–2010) | 84 | 114.7 mm |
| 全时段 | 203 | 94.4 mm |
| 自定义(2004–2009) | 72 | 118.9 mm |

与「全时段」之差:**GRACE 惯例最大 848 mm / RMS 65 mm**,
自定义(2004–2009)最大 **942 mm / RMS 72 mm** —— 与信号本身同量级。
所以这不是一个可以替用户默认的选项。

三条实现约束:

1. **窗口为空必须报错**,绝不退化成全时段(那会悄悄换掉静态场基准);
   报错时把序列的真实跨度一并给出。
2. **`all` 与旧 `remove_mean` 逐位一致**。踩过的坑:窗口覆盖全部历元时若也走
   花式索引 `C[:, :, sel]`,副本的内存布局变了、NumPy 的成对求和分块跟着变,
   实测能差 1e-19 —— 所以全时段时直接用原数组,并且没有非有限值时用 `.mean()`
   而不是 `nanmean()`(与 MATLAB 的 `'omitnan'` 语义一致,但少一层掩膜机制)。
3. **口径写进 `meta`**(`reference_removed` + `mean_window`),落盘后的文件
   自己说明得清是拿哪一段做的基准。

日期写法很宽松(`2004-01-01` / `2004-01` / `2004` / `2004.5`),且**起点补
01-01、终点补 12-31** —— `--mean-to 2009` 若补成 2009-01-01 会少算 11 个月
而且不报错,这类"静默少算"最难发现。

### 4.9 水平形变:算子、极点与接口

#### 4.9.1 公式(与径向同源,推导一遍钉死)

GRACE 给的是**无量纲重力位系数** `ΔC_nm, ΔS_nm`(4π 归一化、无 CS 相位)。
记标量场

```
S(θ,λ) = Σ_{n,m} [ ΔC_nm cos mλ + ΔS_nm sin mλ ] · P̄_nm(cosθ)
```

则载荷引起的位移是 `1/R` 因子恰好约掉之后的**同一族**公式
(`V_load,n ∝ σ_nm/(2n+1)`,而 `σ_nm ∝ (2n+1)` ⇒ `(2n+1)` 约掉):

```
u_r = Σ_n F^r_n · S_n                     F^r_n = R·h′_n/(1+k′_n)      ← 已有
u_H = Σ_n F^h_n · ∇_H S_n                 F^h_n = R·l′_n/(1+k′_n)      ← 新增
```

球面上 `R·∇_H S = ∂S/∂θ · θ̂ + (1/sinθ)·∂S/∂λ · λ̂`,`θ̂` 指向**南**,于是两个分量:

```
u_N(北向) = −Σ_n F^h_n · ∂S_n/∂θ
u_E(东向) = +Σ_n F^h_n · (1/sinθ) · ∂S_n/∂λ
```

派生量(旋转不变量 / 方向):

```
magnitude = hypot(u_N, u_E)                    处处有定义,含两个极点
azimuth   = atan2(u_E, u_N)  (→ [0,360) 自北顺时针)
```

> 单位与量级锚点:随包 `l′` 表给出 `F^h_n ∈ [1.80e5, 6.44e5] m`(n=1..96),
> 约为径向因子的 2%~36%;`|C| ~ 1e-10` 的 GRACE 系数实测得到
> `u_N ~ 0.7 mm`、`u_E ~ −1.4 mm`、`u_r ~ −72 mm` —— 同为 mm 量级。
> **若谁给水平乘了 `(2n+1)/3` 或 `ρ̄/ρ_w`,立刻差 1e7 倍;这是最好的自检。**

#### 4.9.2 两个新算子(都与时间无关,天然支持批量)

```python
def q_at_pole_m1(nmax, t_pole) -> np.ndarray:

```

**极点结论(实测,不是推导猜测)**:

| 量 | 极点行为 | 处理 |
| --- | --- | --- |
| `∂P̄_nm/∂θ` | 全部有限 | 递推求导,无特判 |
| `P̄_nm/sinθ`,m=1 | **有限且非 0**(`Q_11 = √3 ≈ 1.7320508076`) | 用 `q_at_pole_m1` 的递推极限 |
| `P̄_nm/sinθ`,m≥2 | 恰为 0 | 极点行置 0 |
| `u_N, u_E` | 本身有限;但"北/东"方向在极点无定义 | 照算,但**不在极点画箭头**;`magnitude` 可用 |

> 反例警告:`P̄_n1/sinθ` 在北极的极限是 `√3`(不是 0、更不是 NaN)。
> 实测把极点写成 0 会把 `u_E` 打掉一个有限值(纯 `C_11` 场在极点
> `u_E = −√3`);写成 NaN 则整张图报废。这条必须进回归测试。

#### 4.9.4 `SCHCoeffs` 与滤波

- `horizontal_displacement` **不改变系数本身**:`degree_factors` 给出的 `F^h_n`
  照样可以乘进 `weights_scale`,`synthesize_horizontal` 与
  `apply_degree_filter` 完全兼容。
- **高斯平滑照旧只施加一次**:`W_n` 是逐阶对角乘子,球面卷积与 `∇_H` 可交换,
  所以"先乘 `W_n` 再求梯度"≡"先求梯度再平滑"。报告里要写清施加顺序,
  与径向**共用同一个 `gaussian_km` 参数**(不新增参数名,避免"空间/时间核"混淆)。
- `SHCoeffs` **不需要**任何新字段:矢量性体现在**综合算子**与**产品层**,不在容器。

#### 4.9.5 水平形变也走 FFT(与标量共用同一条经度加速)

`u_N` 与 `u_E` 的经度依赖同样是 `cos mλ/sin mλ`,所以可以各建**一个复谱**
再各做一次 IFFT:

```
F_N,m(θ,t) = −Σ_n F_n (∂P̄_nm/∂θ) · (C_nm − i S_nm)
F_E,m(θ,t) = +i·m·Σ_n F_n (P̄_nm/sinθ) · (C_nm − i S_nm)
u_N = Re Σ_m F_N,m e^{imλ}        u_E = Re Σ_m F_E,m e^{imλ}
```

- 与标量路径同一个 `nlon·Re(ifft(...))`,同样的适用条件与回退规则(§6.5.5);
- **`m=0` 只填 `F_N` 谱,不填 `F_E`**(因子 `m=0` 使 `u_E` 的零阶项恒为 0,
  而 `∂P̄_n0/∂θ ≠ 0` 使 `u_N` 的零阶项非零)—— 漏掉它会让 `u_N` 系统性出错;
- 实测与直接算子一致(u_N 9.9e-15、u_E 1.6e-14 相对场量级,含极点行 9.9e-16),
  代价从"径流的 2.2~3.0 倍"降到"FFT 径流的约 1.8 倍"(两次 IFFT vs 一次)。

## 6. 性能与内存预算

### 6.1 核心实测:批量为什么必须是"一次调用"

```
1° 全球 181×360 = 65,160 点,nmax=60,K=24 个真实 CSR 历元:
    一次调用 ntime=K : 2.49 s
    逐历元循环 K 次  : 28.14 s
    加速比           : 11.28x
    最大差           : 0.000e+00        ← 本机逐位相同
    外推 203 历元    : 批量 ≈ 21 s,逐历元 ≈ 238 s
```

原因很直白:勒让德递推只依赖**纬度**,与时间无关。逐历元调用会把同一套递推
重算 203 遍;一次调用只算一遍,然后把这个 `(n-m+1, npoints)` 的核
对 `(n-m+1, ntime)` 的系数块做一次 BLAS-3 矩阵乘。

> 验收判据写 **≤1e-12** 而不是"逐位"(现有 `test_engine.py::test_multitime`
> 就是这么卡的):块矩阵乘的求和顺序可能与单列乘不同。本机实测为 0.0。

### 6.4 水平形变的代价(实测)

同一个目标几何、同一批 `ntime` 历元,**一次调用同时算北 + 东**
(不重复解析几何、不重复算勒让德递推):

```
1° 全球 181×360 = 65,160 点,nmax=60,K=24 历元(取两次最小):
    径向(1 个分量,复用 engine.synthesize) : 1.99 s   → 单历元 0.083 s
    水平(北+东,2 个分量,含导数递推)      : 5.99 s   → 单历元 0.250 s
    倍数 = 2.2x ~ 3.0x(多次实测区间)
    外推 203 历元:径向 ≈ 17~21 s,水平 ≈ 46~51 s
```

> ⚡ 有了 §6.5 的 **FFT 经度路径**,这两行都要换掉:同规模下
> 径向 4.87 s → **0.07 s** 量级、水平(北+东)→ **0.07 s**(74×)。
> 下表保留直接法的数字,因为它是"区域网格/散点"唯一可用的路径,
> 也是 FFT 路径的**对表基准**。

多出来的开销有三块,都是可解释的:

1. `dP̄/dθ` 递推 —— 勒让德那部分的浮点量翻倍;
2. `P̄/sinθ` 一次逐元素除法(每阶 `(nmax−m+1)×npts` 个除法);
3. 每个 `m` 从 1 次矩阵乘变成 4 次(北、东 × cos/sin)。

> 已实测**排除了**一个假象:把 `P̄/sinθ` 用 `legendre_pbar` 全矩阵实现(参考写法)
> 会额外吃 1 GB 内存、代价飙到 **4.81×**;改成与 `P`、`dP` 同一条列循环之后
> 降到 2.2~3.0×。**所以实现必须照 §4.9.2 的流式写法,不许materialize 全矩阵。**

**内存**:`legendre_columns_vec` 每一列在内存里保留 `m`、`m−1`、`m−2` 三阶的
`P`、`dP`、`Q` 三套(6 个 keep 数组 + 当前 `col`/`dcol` + `Q`),峰值约
**9·(nmax+1)·npoints** 个 double;现有 `engine.legendre_columns` 的峰值是

对应预算见 §6.3 直接乘 2。

### 6.5 计算效率:FFT 经度路径(参考 `m2csharp`,实测)

> 这一节回答"批量处理还有个问题是计算效率"。全部数字来自
> [`probes/_probe_fft_backend.py`](probes/_probe_fft_backend.py),

#### 6.5.1 现有直接法的时间去哪儿了(渐近,不是线程)

现有 `engine.synthesize` 对每个 `m` 先算 `cos mλ/sin mλ` 并在**全部 `nlat×nlon`
个点**上做矩阵乘与累加:

```
直接法:  Σ_m (nmax−m+1)·(nlat·nlon)·ntime  =  O(nSHCS·nlat·nlon·ntime)
```

也就是"把经度方向的傅里叶展开对每个格点各做一遍"。而在**规则全球经度网格**上,
经度方向的展开本来就可以用一次 FFT 完成:

```
FFT 路径: O(nSHCS·nlat·ntime)                     ← 只对 n 求和(每阶一个 (nlat,ntime) 谱)
        + O(nlat·ntime·nlon·log nlon)             ← 沿经度做一次批量 IFFT
```

以 1° 全球(`nlat×nlon = 181×360`)、`nmax=60`、`ntime=203` 为例:

```
直接法  ≈ 1891 × 181 × 360 × 203 ≈ 2.5e10 次乘加
FFT 路径 ≈ 1891 × 181 × 203       ≈ 7e7   次乘加  +  181×203 次长度 360 的 FFT
⇒ 运算量相差约 140 倍
```

**这是算法级的差距,不是多线程/多核的差距** —— 观察到的加速比(30~130×)
正是这个量级,换个单核机器也成立(只是绝对时间变慢)。

#### 6.5.2 实测对比(同一台机器:Intel Ultra 7 265K,20 逻辑核)

| 场景 | SHSynth 直接法(纯 Python) | **纯 Python FFT 原型** | m2csharp(C#/.NET8) |
| --- | --- | --- | --- |
| 1° 全球, nmax=60, ntime=24 | 1.7~2.5 s | **0.04 s**(≈50×) | 0.03 s |
| 1° 全球, nmax=60, ntime=203 | 7.8~10.1 s | **0.27~0.31 s**(≈30×) | 0.14 s |
| 1° 全球, nmax=96, ntime=203 | 15.5~16.9 s | **0.41~0.44 s**(≈38×) | 0.15 s |
| 0.5° 全球, nmax=60, ntime=203 | 40.6~41.9 s | **0.76~0.88 s**(≈50×) | 0.42 s |
| 0.5° 全球, nmax=60, ntime=24 | 11.4~13.0 s | **0.09~0.11 s**(≈125×) | — |
| **水平形变** 北+东, 1°, nmax=60, ntime=24 | 4.9 s | **0.07 s**(≈74×) | — |

三条结论:

1. **纯 Python(numpy + scipy.fft)就能拿到 27~125×**,1°×203 历元从 ~10 s 降到 **0.3 s**;
2. 与 C# 实现只差约 **2×** —— 那 2× 来自 C# 的 `Parallel.For` + `Vector.Dot`(SIMD)
   与更省的内存拷贝,**不值得为它引入一套 .NET 运行时**(§9 决策 15);
3. 批量综合从此**基本免费**:203 个历元 0.3 s,真正的成本回到"读文件 + 写盘 + 出图"。

#### 6.5.3 FFT 路径的正确性(必须保持逐点一致)

| 检查 | 实测结果 |
| --- | --- |
| FFT 路径 vs 直接法(1° 全球, nmax=60, ntime=5, 随机系数) | 最大绝对差 **3.3e-22**(相对场量级 ~1e-14) |
| 含 ±90° **极点行** | 最大绝对差 **3.3e-22** |
| 带**逐阶乘子**(模拟高斯滤波 / 单位因子) | 最大绝对差 **4.4e-22** |
| **真实 GRACE gfc** 系数(`|f|~1.0`) | 绝对差 **2.9e-15**(相对 2.9e-15) |
| 水平形变 u_N / u_E(带 `R·l′/(1+k′)`) | 9.9e-15 / 1.6e-14(相对场量级) |
| 水平形变**极点行** `u_E`(直接算子量级 7.2e-02) | 差 **9.9e-16** |

⇒ FFT 路径与直接法是**同一个数学对象**,差别只在浮点求和顺序。

> ⚠️ 实现时必须注意 **`m=0` 对 `u_N` 有贡献**(`∂P̄_n0/∂θ ≠ 0`),对 `u_E` 没有
> (因子 `m=0`)。本方案的原型第一版就因为 `if m == 0: continue` 把 `u_N` 算错了
> 31%,改成"`m=0` 只填 `F_N` 谱"之后立刻降到 1e-15。

#### 6.5.4 ⚠️ 一个不能抄的坑:**m2py / m2csharp 的 FFT 结果整体平移了一个经度格**

拿 m2csharp 当"独立实现对表"时,发现残差**与场成正比**(18%~47%),不是浮点噪声。
逐项定位后结论如下:

| 对照 | 不平移 | 平移 −1 个经度格 |
| --- | --- | --- |
| m2csharp SH→Grid vs SHSynth 直接法(nSH=30, 1°, 宽带系数) | 相对 **2.7e-01** | 相对 **8.7e-14** |
| 同上(nSH=60, 1°, scale=1e-10) | 相对 4.7e-01 | 相对 **1.1e-13** |
| **m2py 自己的 `fft`** vs SHSynth 直接法 | 相对 **2.7e-01** | 相对 **6.2e-15** |
| **m2py 自己的 `direct`** vs SHSynth 直接法 | 相对 **4.6e-15**(不需要平移) | — |

- **m = 0 的项完全不受影响**(任何经度旋转都改不了 `cos0λ`),所以只测 `m=0`
  或只看全球统计量**永远发现不了这个错**;
- 根因是 m2py `_SH2grid_fft` 的收尾式
  `GRID = fliplr(real(ifft(conj(spectrum))) * nc)`:先 `conj` 使经度**反序**,
  `fliplr` 把反序翻回来,却留下一个 **+1 格**的平移 ⇒ 输出第 `j` 列装的是
  `lon = 360·(j+1)/nlon` 处的值,而它的经度向量仍写着 `360·j/nlon`。
- m2csharp 是 m2py 的移植,所以**继承**了同一个平移(它的 `WriteDsaa` 把
  `lon[0]=0` 写进表头,内容却对应 1°)。
- **对本方案的要求**:FFT 路径用朴素 `ifft`(已验证与直接法逐点一致),
  **不要**照抄 `conj`/`fliplr` 那套索引;并且回归测试必须用 **`m≥1`** 的系数
  钉住经度对齐(§7.1)。

#### 6.5.5 适用条件与回退(必须自动判定并报告)

```
可用:规则、整圈、均匀的经度网格(--global-grid;范围网格给到 360 时也成立)
      且 nlon > 2·nmax(否则 m 超过 Nyquist 会混叠)
不可用:区域经度范围、散点、借用网格文件里非整圈的格点  → 直接法
      nlon ≤ 2·nmax                                  → 直接法(并警告)
```

**纬度怎么取不影响判定**(FFT 只在经度方向)。完整的逐类判定与实测见 §6.5.7。

`plan_text` / 汇总里要**明确打印本次走的是哪条路**(以及回退原因),
不许"悄悄换算法"——否则同一份输入换台机器/换个步长就会出现看不出原因的速度差。

#### 6.5.6 内存与两个分块旋钮

- FFT 路径的临时数组是 `(nlat, ntc, nlon)` 复数,按 `time_chunk` 分块:
  0.5° 全球、`ntc=32` 时约 **133 MB**;1° 全球、`ntc=32` 时约 33 MB。
  `time_chunk` 由内存预算自动定(默认 32),**与 `epoch_chunk` 是两件事**:
  - `time_chunk`:FFT 路径内部的临时块大小,**不改变结果**;
  - `epoch_chunk`:整条序列"算一段 → 写出 → 释放"的落盘节奏(§6.3)。
- 有了 FFT 路径,§6.2 的"单历元 0.92 s / 203 历元 ≈21 s"应替换为
  "单历元 ≈1.5 ms / 203 历元 ≈0.3 s";§6.3 的结论不变(内存由**输出数组**决定,
  不再由计算决定)。

#### 6.5.7 FFT 到底适用于哪些目标几何(逐类实测)

> 由 [`probes/_probe_fft_scope.py`](probes/_probe_fft_scope.py) 实测(nmax=60,ntime=24,
> 已预热线程池,每项取 2 次最小)。

**一句话:FFT 只作用在"经度"这一个方向上,所以要求的是"经度是否是整圈均匀采样",
而**与纬度怎么取完全无关**。** 散点是没有任何一条均匀经度轴,所以不适用。

| 目标几何 | FFT | 实测(直接法 → FFT) | 结论 |
| --- | --- | --- | --- |
| 全球规则网格(1°,181×360) | ✅ | 2.13 s → **0.041 s**(**52.5×**) | 主用例 |
| **纬向区域** 20..50°N,经度整圈(31 行) | ✅ | 0.39 s → **0.012 s**(**33.4×**) | **纬度只取一段照样适用** |
| 纬向区域 35..40°N(6 行) | ✅ | 0.05 s → 0.009 s(6.2×) | 行数少时两边都很快,收益自然变小 |
| **经向区域** 70..140°E(71 列),整圈 FFT 后切片 | ⚠️ | 0.054 s → **0.012 s**(4.6×) | 划算,但代价固定=一次整圈 FFT |
| 经向区域 100..110°E(11 列) | ⚠️ | 0.016 s → 0.012 s(1.4×) | 勉强持平;窄区域直接用直接法 |
| 经度**非均匀 / 任意值**(随机、0..90 加密) | ❌ | — | 没有均匀经度轴,只能直接法 |
| **散点**(2 万 / 20 万随机点) | ❌ | 直接法 0.63 / 11.0 s | 见下面"散点怎么办" |
| 散点但**纬度高度重复**(6 万点 / 600 个纬度) | ❌ | 1.93 s → 1.31 s(1.5×) | 可用"查表+归约"小幅加速 |

**散点怎么办(实测,别指望太多)**

散点没有均匀经度轴,FFT 无从下手。有人会想到"按唯一纬度先算 `A_m(θ), B_m(θ)`,
再对每个点做一次 `Σ_m A_m cos mλ + B_m sin mλ`"(理论上少 `≈nmax/2` 倍的乘加),
但**实测在随机散点上反而更慢**:

```
2 万随机点 :  直接法 0.63 s   查表+归约 1.12 s   → 0.6x(更慢)
20 万随机点:  直接法 11.0 s   查表+归约 14.7 s   → 0.7x(更慢)
6 万点 / 600 个不同纬度: 1.93 s → 1.31 s        → 1.5x(略快)
```

原因是直接法的两次矩阵乘是 **BLAS-3**(缓存友好、向量化),而"查表+归约"每阶都要
做一次 `A[m][inv]` 的**花式索引搬运**,是纯内存带宽瓶颈;只有当唯一纬度远少于点数
(卫星重复轨道、按纬度带抽样的台站)时,省下的算术才盖过搬运成本。

⇒ 因此本方案对散点**保持现有直接法**,不引入"查表+归约"(实测收益不稳定)。
若用户确有海量散点需求,再考虑两条**可选**路线(都不在本版范围):
① 细网格 FFT + 插值(近似,必须显式报告插值误差);② NUFFT(要新依赖)。
**绝不把"近似"包装成"精确"**——这是 §3 原则 8 的直接要求。

**经向区域的两条路**

1. **整圈 FFT 后切片**(本版建议):
   要求区域的经度值与某个"整圈、均匀、同相位"的网格**逐点重合**
   (例如 70..140 at 1° 与 0..359 at 1° 重合)。代价固定 = 一次整圈 FFT,
   所以区域越窄收益越小(71 列 4.6×,11 列 1.4×)。实现上就是
   `synthesis_grid_fft(lat, 整圈lon)` 之后按索引切片,**数值仍与直接法一致**。
2. 直接法:窄区域(≲30 列)或经度不落在整圈网格上时,直接用直接法。

> 实现细节:`fft_path_applicable` 目前要求整圈网格**从 0° 起**。整圈网格从任意
> 相位起(如 0.5° 起、1° 间隔)在数学上同样可 FFT(相位即一次 `roll`)。
> P3 实施时应把判据放宽成"均匀间隔 + 恰好覆盖整圈",相位差用 `roll` 吸收,
> 并加对应的往返测试。

**一条硬条件(不是"慢一点",而是"会算错")**

```
必须  nlon > 2·nmax          (否则 m ≥ nlon/2 会折叠到低频,Nyquist 混叠)
nmax=60 时:经度步长必须 ≤ 360/121 ≈ 2.97°
    1°  → nlon=360  ✅        2°  → nlon=180  ✅
    3°  → nlon=120  ❌        5°  → nlon=72   ❌        10° → nlon=36  ❌
```

不满足时**必须回退直接法**并说明;不许"近似凑一下"。粗网格本来点数就少
(5° 全球仅 72×37),直接法也不慢,损失有限。

> 顺便可以给一条**用户有用的提示**:当 `nlon < 2·nmax+1` 时,这张网格本身
> 已经分辨不出 `nmax` 阶的场(最短波长 `360/nmax` 度 < 2 倍步长)。
> 这与用哪种算法无关,建议在汇总里提醒"网格步长偏粗,建议 ≤ 360/(2·nmax) 度"。

**结论(给用户手册的一句话)**

> **规则、整圈、均匀的经度网格 → 走 FFT(快 30~130 倍,含纬度区域);
> 经度是区域/非均匀、或散点 → 走直接法(结果一样,只是慢)。
> 软件会自动选,并在汇总里写明这次走的是哪条路。**

  **`2020-03-01T00.00.00.00` 点号写法**;头与文件名冲突必须**报告**(构造冲突样本)。
- **与 legacy 对表**(用真实文件,只读,缺失则 `skipif` 并说明):
  `decimal_years(mid)` vs `*_TimeInfo.dat` 第 4 列,**按日期配对**,≤1e-6;

- 十进制年 ↔ `datetime64` 往返;`missing()` / `duplicates()` / `is_regular` 边界;
  在真实 `3_grids` 轴上必须报出 19 处 >40 天缺口,其中第一处 = 98 天

### 7.3 序列读取(P2)

- 203 个真实 gfc → `(61,61,203)`,与 `CSR_rawSH60_total_216.dat` 重叠历元比对
  (必须**按日期配对**,不是按下标:两套历元集合不同,203 vs 216)。
  ⚠️ **判据已按实测修正**:老文件是 ``%.10g`` 写的,**它自己只有约 9 位有效数字**,

## 8. 明确不做(诚实清单,与 SHKit 方案 §8 同风格)

1. **不做时间滤波 / 插补 / 重采样**:那是时间域算子,属 SHKit `timeseries.py` 的地盘。
   SHSynth 只做"前向建模 + 产品化",时间算子最多提供"去参考历元 / 去均值"
   这两个产品必需项(且默认不启用)。
2. **不做 dask / 延迟加载**:输入场整体进内存,超出预算的答案是
   "降分辨率或分历元区间跑",不是引入第二套 IO 栈。
3. **不做完整统计推断**:只给线性 + 固定周期(1 / 0.5 年)最小二乘的 1σ 与 SNR;
   不做 AR(1) 噪声模型、不做 Mann-Kendall、不做显著性检验的完整理论。
4. **不做自动剔除 / 自动插补可疑历元**:只报告(MAD 离群返回索引 + 中文说明)。
5. **不做 GRACE 专用改正**:低阶项替换(J1/J2)、GIA、去相关(P4M6/P3M13)、DDK
   都是 SHKit 可选的 P5;SHSynth 只负责把结果**读进来画出来**。
6. **不做球谐分析(场 → 系数)**:那是 SHKit。SHSynth 只准备与读取路径 ②的输入。
7. **不做 MP4 硬依赖**:无 ffmpeg 时降级 GIF 并说明;不把 `imageio-ffmpeg` 塞进安装包。
8. **不做多进程/并发**:批量收益来自"一次调用",不是并行进程;
   引入进程池会与现有后台线程 + 协作取消的架构打架。
9. **不做平面投影掩膜的重采样**:区域平均的掩膜必须是等经纬网格或球面多边形;
   遇到平面米制坐标要**明确报错**(沿用 `_guard_geographic_coords` 的做法)。
10. **不保证与 MATLAB 中间产物逐位相同**(版本/滤波口径不同),
    只保证**能读能写能对账**,差异必须可解释。
11. **不做应变/旋转张量与重力梯度**:水平形变只给**北/东两个位移分量**与
    派生的大小/方位角。应变张量(`ε_NN, ε_EE, ε_NE`)、旋转、面膨胀需要
    位移的**空间导数**,虽然同源但会再引入一层算子与极点处理,另立。
12. **不做三维位移的深度依赖**:只算**地表**形变(GRACE 载荷研究的常规口径),
    不做分层/深度剖面。
13. **不引入 cftime / 第三套时间栈**:m2py 的查看器用 `cftime.num2date`,
    SHSynth 内部统一 `datetime64`(`3_grids` 就是 `datetime64` 坐标)。
14. **不做时变勒夫数**:一律用随包静态表(PREM / Wang 2012);
    不按历元换表、不做黏弹(ICE-6G 之类)时间依赖改正。
15. **不引入 .NET / C# 运行时**(即不把 m2csharp 打进产品):纯 Python 的 FFT 路径
    已经拿到 C# 版本约一半的速度(§6.5.2),而引入托管运行时会给安装包加上
    几十 MB、一套额外的许可与部署面;**只把 m2csharp 当可选的外部对表工具**
    (`docs/probes` 里 `skipif(不存在)`)。
16. **不做 GPU / CUDA**:目标用户是笔记本/台式机,没有可依赖的 GPU;
    也不做多进程(§8 第 8 条)。
17. **不把 `pyfftw` / `numba` 列为硬依赖**:`scipy.fft` 已经够(实测 27~125×);
    若日后确实要再榨 2×,作为**可选加速**另开,不进 `requirements.txt` 的必需项。
18. **不做 FFT 路径的"区域网格凑整圈"**:区域经度范围一律走直接法,
    不把区域数据零填充成整圈再 FFT(那会引入边界伪影,且用户看不出)。

## 12. 附录:落盘契约(冻结)

### 12.1 与 SHKit 的 `series_nc`(系数序列)

两包靠**文件**互操作,不靠 import。以下键名与维度**冻结**,任何一侧改动都要同步。

| 项 | 约定 |
| --- | --- |
| 维度 | `time = N`,`n = L+1`,`m = L+1` |
| 系数变量 | `c(time,n,m)`,`s(time,n,m)`(float64;读的时候也接受 `C`/`S`) |
| 时间坐标 | `time(time)`,`datetime64[ns]`;读的时候也接受 `int32 + units="days since …"` |
| 阶次坐标 | `n(n)`、`m(m)` 整数;缺失时按稠密方阵推 |
| 全局属性 | `norm="4pi"`,`csphase=1`,`field_unit`,`nmax`,`gaussian_km`,`tide_system`,`center`,`mission`,`product`,`rl`,`source_files`,`time_source`,`coverage_start`,`coverage_end`,`created`,`producer` |
| 写入方 | SHKit `write_coeffs(layout='series_nc')` 与 SHSynth 同一套键名 |
| 读取方 | 双方都要**宽容读**:维度顺序、变量大小写、坐标缺失、时间缺失(降级为序号 + 警告) |
| 三角互操作 | `*.dat`:首行 = 历元编号表头,主体 `(2*NC, ntime)`;`*_TimeInfo.dat`:`[idx, y_start, y_end, y_mid]`,口径见 §1.3 缺陷 C |

### 12.2 水平形变场序列(矢量)

**一个文件装两个分量**,共享 `lat/lon/time` 三个坐标 —— 与用户 `3_grids` 那种
`(time,lat,lon)` 产品同构,xarray / Panopy / GMT 直接可开。

```
dimensions:  time = N ; lat = nlat ; lon = nlon
variables:   north_displacement(time,lat,lon)  float32/float64
             east_displacement (time,lat,lon)  float32/float64
             magnitude         (time,lat,lon)  可选,hypot(N,E)
             azimuth           (time,lat,lon)  可选,度,[0,360) 自北顺时针
             time(time) datetime64[ns] ; lat(lat) ; lon(lon)
属性(每个分量变量):
    units        = "m"(或 --scale mm 时 "mm")
    long_name    = "northward surface displacement due to surface mass load"
                   / "eastward surface displacement due to surface mass load"
    comment      = "u_H = Σ_n R·l'_n/(1+k'_n) ∇_H S_n;4π norm, no CS phase"
    不写 standard_name —— CF 没有对应标准名,宁可不写也不编一个(诚实优先)
全局属性:
    field_unit="horizontal_displacement", love_numbers="PREM/Wang2012 (load l')",
    gaussian_km, nmax, source_coeffs, time_source, producer="SHSynth", created
```

| 边界情况 | 约定 |
| --- | --- |
| 极点行 | `north`/`east` **照算且有限**(用解析极限);但文档与图上都不把极点的方向当有意义的量 |
| `magnitude` | 极点同样有效(旋转不变量) |
| `--scale mm` | 只改数值标度与 `units` 字符串,**不改 `field_unit`**;报告里显式打印 |
| 单分量导出 | 允许(只写 `north` 或 `east`),但要在 `comment` 里写明"只有一个分量" |
| 与 EWH 同时导出 | 允许,同一个文件里再放一个 `ewh` 变量即可(共享 `lat/lon/time`) |
